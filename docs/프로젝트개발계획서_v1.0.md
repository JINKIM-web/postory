## 1. 프로젝트 개요

### 1.1 목표
> 사진 몇 장과 짧은 메모만으로, 사용자가 **수정 부담 없이 게시할 수 있는 콘텐츠 품질**을 검증한다. (명세서 20.1)

**MVP = Phase 1A + 1B + 1C** (명세서 38장)

### 1.2 핵심 성공 지표 (MVP 베타 기준)

| 지표 | 정의 | 목표 (초기 가설) |
|---|---|---|
| **Copy-ready Rate** | AI 최종본 대비 편집 거리 X% 이하로 Copy된 콘텐츠 비율 (명세서 39.3) | 60% 이상, X = 10% |
| Unsupported Fact 발생률 | Evidence 출처가 없는 문장 비율 (샘플 수동 검수 병행) | 2% 이하 |
| 생성 완료율 | Create 진입 → 콘텐츠 생성 완료 | 70% 이상 |
| 생성 1건당 비용 | UsageLog 기준 (명세서 40.5) | Phase 0 측정 후 확정 |
| 생성 소요 시간 | 업로드 완료 → Blog 초안 표시 (Smart Question 응답 시간 제외) | 60초 이내 |

### 1.3 범위 요약

| 구분 | 포함 | 제외 (Phase 2) |
|---|---|---|
| 입력 | 사진 1~10장, Quick Text, Category/Goal/Tone/Platform, 광고·협찬 여부 | My Voice, Brand Profile |
| AI | 이미지 분석, EXIF 촬영일시, Evidence, Smart Question, Master Story, 4채널 생성 | 성과 기반 추천, Blog Intelligence |
| 품질 | 규칙 기반 점검 + LLM 검토·부분 재작성·재검증 | 사용자 정의 금칙어(L4), 브랜드 톤 점수 |
| 출력 | Rich/Plain Copy, 이미지 ZIP, .txt, 수동 게시 완료 표시 | 자동/예약 게시, 영상 생성 |

## 3. 시스템 구성

### 3.1 기술 스택 (명세서 28~31장 확정 사항)

| 영역 | 선택 | 비고 |
|---|---|---|
| Frontend | React + Vite + TypeScript, Tailwind CSS, TipTap | TipTap은 Sprint 1 스파이크 후 확정 (명세서 45 #12) |
| 상태·데이터 | TanStack Query, Zustand(에디터 로컬 상태) | 제안 |
| Backend | Node.js + Express + TypeScript | SSE로 단계별 진행 전송 |
| 스키마 | Zod (Master Story, Quality Issue, API DTO) → OpenAI Structured Output JSON Schema로 변환 | 명세서 30장 |
| DB / Auth / Storage | Supabase (Postgres, Auth, Storage, RLS) | 무료 플랜 일시정지 정책 모니터링 |
| 이미지 처리 | sharp (리사이즈·EXIF 제거), exifr (촬영일시 추출) | 제안 |
| ZIP | archiver (스트리밍) | 제안 |
| AI | OpenAI API — 경량 모델(분류·점검) / 상위 모델(본문) 분리 | 모델 선정은 Phase 0 (명세서 45 #4) |
| 테스트 | Vitest, Playwright, 품질 골든셋 평가 스크립트 | 6장 |

### 3.2 저장소 구조 (pnpm 모노레포 제안)

```text
postory/
├─ apps/
│  ├─ web/                 React + Vite
│  │  └─ src/
│  │     ├─ routes/        home, create, projects/:id/(processing|questions|editor), library, auth
│  │     ├─ features/      create, evidence, questions, editor, quality, copy, library
│  │     └─ components/    AppSidebar, TopBar, ... (4.2)
│  └─ api/                 Express
│     └─ src/
│        ├─ routes/
│        ├─ pipeline/      analyze, evidence, questions, masterStory, writers/*, quality/*
│        ├─ quality/       rules(forbidden, claim, keyword, generic, length), review, rewrite, verify
│        ├─ media/         upload, exif, resize, zip, stock
│        └─ llm/           client, prompts, usage logging, retry
├─ packages/
│  ├─ shared/              Zod 스키마, 타입, platform_rules.json, 이벤트 타입
│  ├─ dictionaries/        금칙어·Claim·AI 상투 표현 사전 (업종 태그별)
│  └─ ui/                  디자인 토큰 (Tailwind preset), 공통 컴포넌트
├─ supabase/migrations/    스키마 + RLS 정책
├─ eval/                   품질 골든셋 + 평가 스크립트
└─ docs/
```

### 3.3 생성 파이프라인과 SSE 단계
처리 화면의 6단계(벤치마크 11장)를 백엔드 단계와 1:1로 맞춘다. 단계마다 결과를 DB에 저장하여 실패 시 해당 단계부터 다시 실행한다 (명세서 40.2).

| UI 단계 | SSE 이벤트 | 백엔드 처리 | LLM 호출 |
|---|---|---|---|
| 1. 사진 분석 | `analyze_images` | 분석용 저해상도본으로 Visual Fact 추출, 얼굴 감지 경고 | 경량 1회 (배치) |
| 2. 기억 정리 | `organize_memory` | Quick Text → Confirmed Fact, EXIF → Metadata Fact | 경량 1회 (1과 병합 검토) |
| 3. 필요한 정보 확인 | `check_missing` | Unknown 도출, Smart Question 0~4개 생성 → 질문 화면으로 분기 | 경량 1회 |
| 4. 스토리 구성 | `compose_story` | Master Story (Structured Output) | 상위 1회 |
| 5. 콘텐츠 작성 | `write_content` | 선택 채널별 작성 (채널 단위 저장, 부분 실패 허용) | 상위 채널 수만큼 |
| 6. 품질 검토 | `review_quality` | ① 규칙 → ② 검토 → ③ 부분 재작성 → ④ 재검증 (명세서 10.1) | 채널당 최대 2회 |

> 생성 1건(Blog 단독) LLM 호출 상한: 약 6회. Phase 0에서 실측 후 확정한다.

## 6. 품질 보증 계획

### 6.1 테스트 범위

| 유형 | 대상 | 도구 |
|---|---|---|
| 단위 | 규칙 기반 점검(금칙어·Claim·키워드 빈도·길이), EXIF 처리, Zod 스키마 | Vitest |
| 통합 | API + Supabase(RLS 포함), SSE 단계 재개 | Vitest + 로컬 Supabase |
| E2E | 업로드 → 질문 → 생성 → 수정 → 복사 → ZIP | Playwright |
| 수동 | 네이버 붙여넣기 (PoC 매트릭스 재실행), 모바일 웹 | 체크리스트 |

### 6.2 AI 품질 평가 (골든셋)
LLM 출력은 단위 테스트로 보장할 수 없으므로, 프롬프트·모델·사전을 바꿀 때마다 골든셋을 돌려 회귀를 막는다.

- **구성:** Category 8종 × 입력 3건 + 금지 사례 (Stitch 시안 2.4 #9처럼 입력에 없는 사실을 쓴 예시)
- **자동 지표:** Evidence 출처 없는 문장 비율, L1 금칙어 잔존 수, 채널 길이 제약 위반 수, 재검증 실패율, 호출 수·비용·시간
- **수동 지표:** 2인 블라인드 평가 "거의 고치지 않고 올릴 수 있다" (5점 척도)
- **합격선:** M1 Unsupported Fact 5% 이하 → MVP 출시 2% 이하, L1 잔존 0건

### 6.3 완료 정의 (Definition of Done)
- 명세서 해당 장의 요구사항 충족, 2.4 보정 사항 반영
- 단위·통합 테스트 통과, 핵심 플로우 E2E 통과
- RLS로 다른 사용자 데이터 접근 불가 확인
- AI 관련 변경은 골든셋 평가 결과를 PR에 첨부
- 신규 이벤트는 EventLog 스키마에 등록
