## 1. 문서 개요

### 1.1 프로젝트명
**AI Content Studio** *(가칭)*

### 1.2 프로젝트 목적
사진 몇 장과 짧은 텍스트만 입력하면, AI가 사용자의 실제 경험과 제공 정보를 바탕으로 **게시 가능한 수준의 블로그·SNS 콘텐츠를 생성**한다. 생성한 콘텐츠는 **Blog, Facebook, Instagram, YouTube Shorts**에 맞게 변환하여 복사·저장·배포할 수 있도록 하는 웹앱을 개발한다.

본 서비스는 단순한 AI 문구 생성기가 아니며, 다음을 핵심 가치로 한다.

- 복잡한 프롬프트 없이 쉽게 사용할 수 있을 것
- AI 초안 수준이 아니라 **실제 게시 가능한 품질**을 제공할 것
- 사용자가 주지 않은 정보를 AI가 임의로 만들어내지 않을 것
- 하나의 원본 스토리를 각 플랫폼 특성에 맞게 재구성할 것
- 블로그 글은 검색 품질, 가독성, 금칙어, 과장 표현, 키워드 반복 등을 자동 점검할 것
- 네이버 블로그는 자동 게시가 아닌 **고품질 Rich Copy / Plain Text Copy** 방식으로 지원할 것
- 유료 외부 API는 원칙적으로 사용하지 않는다. OpenAI API만 예외로 허용하며, 무료 API와 오픈소스를 우선 활용할 것

### 1.3 적용 범위
- MVP 출력 언어: **한국어** (다국어 지원 여부는 45. 미결 사항 참조)
- MVP 대상 플랫폼: Web (데스크톱 우선, 모바일 브라우저 대응)

### 1.4 용어집

| 용어 | 정의 | 데이터 필드 |
|---|---|---|
| **Category** | 콘텐츠 주제 분류 (여행, 일상, 카페, 맛집, 제품, 서비스, 개인 브랜딩, 정보/노하우) | `category` |
| **Goal** | 작성 목적 (정보 전달, 후기, 검색 유입, 개인 브랜딩, 제품 홍보, 방문 유도, 판매 유도, 경험 공유) | `goal` |
| **Tone** | 문체 톤 (담백한, 친근한, 전문적인, 감성적인, 세련된, 유쾌한) | `tone` |
| **Platform** | 출력 채널 (Blog, Facebook, Instagram, YouTube Shorts) | `platforms[]` |
| **Quick Text** | 사용자가 입력하는 짧은 메모·기억 텍스트 | `quick_text` |
| **Evidence** | 콘텐츠 작성 근거 정보 (Confirmed / Visual / Metadata / Unknown) | `evidence_item` |
| **Smart Question** | 부족한 정보를 보강하기 위해 AI가 하는 추가 질문 | `smart_question` |
| **Master Story** | 모든 채널 콘텐츠의 공통 원본이 되는 구조화 데이터 | `master_story` |
| **Content Version** | AI 생성본, AI 재작성본, 사용자 수정본 등 콘텐츠의 각 버전 | `content_version` |
| **Copy-ready Rate** | 생성 콘텐츠 중 큰 수정 없이 복사된 비율 (39장 정의) | - |
| **Stock Image** | Pixabay/Unsplash 등 외부 무료 이미지 | `source` |

## 2. 제품 비전

### 2.1 한 줄 정의
> **사진 몇 장과 한 줄의 기억만으로 블로그와 SNS에 바로 올릴 수 있는 콘텐츠를 만드는 AI 콘텐츠 제작·배포 웹앱**

### 2.2 제품 포지셔닝
기존 AI 글쓰기 서비스가 "AI에게 글을 써달라고 요청하는 도구"라면, 본 서비스는 다음과 같이 정의한다.

> **사용자가 가진 사진과 실제 경험에서 AI가 소재를 찾아 구조화하고, 게시 가능한 콘텐츠로 완성하는 도구**

### 2.3 핵심 차별화
1. **Publish-ready Quality** — 초안이 아닌 게시 가능한 완성본 제공
2. **Evidence-based Generation** — 실제 입력 정보와 이미지에서 확인되는 사실만 바탕으로 작성
3. **One Story → Multi-channel** — 하나의 원본 스토리를 Blog, Facebook, Instagram, YouTube Shorts용으로 변환
4. **Simple Input** — 사진 + 짧은 메모 + 목적 선택만으로 생성
5. **Content Quality Engine** — 금칙어, 과장 표현, 키워드 반복, AI 상투 표현, 검색 품질 자동 점검
6. **Blog-first Strategy** — 블로그를 Long-form 원본 콘텐츠의 중심에 두고 SNS 콘텐츠로 확장

## 3. 타깃 사용자

### 3.1 1차 타깃

#### 개인 브랜딩 사용자
강사, 컨설턴트, 코치, 프리랜서, 크리에이터, 전문직, 작가, 디자이너, 마케터

#### 제품/서비스 홍보 사용자
소형 브랜드, 온라인 셀러, 자사몰 운영자, 인스타그램 판매 계정, 카페, 음식점, 로컬 비즈니스, 뷰티/패션/라이프스타일 사업자, 서비스 사업자

> 홍보 사용자는 광고·협찬 표기 의무와 민감 산업 표현 규제의 적용을 받을 수 있으므로 41.2의 정책을 적용한다.

### 3.2 사용자의 핵심 문제
- 무엇을 올릴지 매번 고민해야 함
- AI가 쓴 글의 품질이 낮아 고치는 데 시간이 많이 듦
- AI 특유의 상투적인 문체가 강함
- 블로그와 SNS용 콘텐츠를 따로 작성하기 번거로움
- 사진은 있지만 글을 쓰기 어려움
- 플랫폼별 톤과 형식 차이를 직접 맞추기 어려움
- 콘텐츠 제작과 발행이 분리되어 있음

## 4. 지원 콘텐츠 채널

### 4.1 1차 지원 대상
- Blog (네이버 블로그 Copy 중심)
- Facebook
- Instagram
- YouTube Shorts

### 4.2 채널별 기본 역할

#### Blog
- Long-form 원본 콘텐츠
- 상세 경험, 정보, 스토리 중심
- 검색 유입 고려
- 네이버 블로그용 Copy 기능 제공

#### Facebook
- 중간 길이의 스토리형 포스트
- Hook → Story → Key Message → CTA

#### Instagram
- 시각 중심, 짧은 캡션
- Hook, 개인적 느낌, CTA, Hashtag

#### YouTube Shorts
- Short-form 영상 스크립트
- Hook, Scene 구성, Overlay Text, Caption, Description, Hashtag

### 4.3 채널별 제약 및 기본값

플랫폼 제약은 정책이 수시로 바뀌므로 **코드에 하드코딩하지 않고 설정 파일(platform_rules)로 관리**한다. 아래 값은 개발 착수 직전에 각 플랫폼 공식 문서로 다시 확인한다.

| 채널 | 항목 | 기준 (재확인 필요) | 서비스 기본값 |
|---|---|---|---|
| Blog | 제목 | 플랫폼 제한 없음 | 내부 권장 길이 설정 |
| Blog | 본문 | 제한 없음 | Category별 권장 분량 설정 |
| Facebook | 본문 | 매우 긴 텍스트 허용 | 중간 길이 (내부 기준) |
| Instagram | 캡션 | 최대 약 2,200자 | 짧은 캡션 우선 |
| Instagram | 해시태그 | 개수 제한 있음 (최근 축소 정책 여부 확인) | 5개 이하 권장 |
| YouTube Shorts | 제목 | 최대 100자 | 짧은 제목 우선 |
| YouTube Shorts | 설명 | 최대 5,000자 | 짧은 요약 + 해시태그 |
| YouTube Shorts | 영상 길이 | Shorts 최대 길이 정책 확인 | 스크립트 기본 15~30초 |

생성 결과가 제약을 넘으면 Quality Engine의 규칙 기반 점검(10장)에서 경고하고 자동으로 줄여 쓸 것을 제안한다.

## 6. 전체 사용자 여정

```text
사진 업로드 + Quick Text
        ↓
Category 선택 → Goal 선택 → Tone 선택 → Platform 선택
        ↓
AI 이미지/텍스트 분석 (+ EXIF 촬영일시 추출)
        ↓
Evidence Engine
        ↓
Smart Question (0~4개, 필요 시에만)
        ↓
Master Story 생성
        ↓
AI Content Engine (선택한 Platform만 생성)
   ├─ Blog
   ├─ Facebook
   ├─ Instagram
   └─ YouTube Shorts
        ↓
Content Quality Engine
        ↓
사용자 수정 / 승인
        ↓
[MVP]     Copy / Save / Download / 게시 완료 표시(수동)
[Phase 2] 자동 게시 / 예약 게시
```

- **Blog-first:** 사용자가 Blog를 선택하지 않아도 Master Story가 원본 역할을 한다. Blog를 선택하지 않으면 블로그 본문은 생성하지 않는다.

## 7. 핵심 기능 정의

### 7.1 Smart Input

#### 목적
복잡한 프롬프트 입력 없이 최소한의 입력으로 콘텐츠를 생성한다.

#### 입력 항목
| 항목 | 필수 | 비고 |
|---|---|---|
| 사진 | 필수 | 1~10장 (MVP), 파일 형식·용량 제한 (40장) |
| Quick Text | 권장 | 비어 있으면 Smart Question 비중 증가 |
| Category | 필수 | 5장 |
| Goal | 필수 | 아래 예시 |
| Tone | 선택 | 기본값: 담백한 |
| Platform | 필수 | 1개 이상 |
| 광고·협찬 여부 | 선택 | 경제적 이해관계가 있으면 체크 (41.2) |

#### Goal 예시
정보 전달, 후기, 검색 유입, 개인 브랜딩, 제품 홍보, 방문 유도, 판매 유도, 경험 공유

#### Tone 예시
담백한, 친근한, 전문적인, 감성적인, 세련된, 유쾌한

---

### 7.2 Evidence Engine

#### 목적
사용자가 제공하지 않은 경험이나 사실을 AI가 임의로 만들어내지 않도록 한다.

#### 데이터 구분

**A. Confirmed Fact** — 사용자가 직접 입력한 정보 (Quick Text, Smart Question 답변)
- 예: "토요일 방문", "파스타를 주문", "다시 방문하고 싶다"

**B. Visual Fact** — 이미지에서 확인 가능한 정보 (신뢰도 high / low 구분)
- 예: "야외 테라스 좌석이 보임", "메뉴판 사진이 있음", "특정 음식이 보임"

**C. Metadata Fact** — 이미지 메타데이터에서 추출한 정보
- 예: EXIF 촬영일시
- 사용자 확인 후 Confirmed Fact로 승격한다. 확인 전에는 날짜를 본문에 확정적으로 쓰지 않는다.
- **GPS 위치 정보는 활용하지 않으며 저장 전에 제거한다** (개인정보 보호, 32장).

**D. Unknown** — 확인되지 않은 정보
- 예: 가격, 직원 친절도, 정확한 영업시간, 대기 시간, 음식 재료, 실제 판매량

#### 정책
1. Unknown 정보는 AI가 생성하지 않는다. 필요하면 Smart Question으로 묻고, 답이 없으면 **생략**한다.
2. Visual Fact 중 신뢰도가 낮은 것은 **관찰 표현에 한해 완곡한 표현을 허용**한다.
   - 허용: "창가 쪽은 햇빛이 잘 드는 것처럼 보였다"
   - 불허: 가격, 효능, 성분, 순위, 인증, 타인의 평가는 완곡하게라도 쓰지 않는다.
3. 사용자 평가(의견)와 객관적 사실은 Master Story에서 구분하여 저장하고, 본문에서도 구분해 쓴다.
4. 모든 Evidence는 출처(Quick Text / 답변 / 이미지 ID / 메타데이터)를 기록한다. 이 출처는 Evidence Consistency Check(10장)의 근거가 된다.

### 7.3 Smart Question

#### 목적
정보가 부족할 때 AI가 지어내는 대신, 사용자의 실제 기억을 최소한의 질문으로 보강한다.

#### 기본 정책
- 질문 수: **0~4개** (필요 없으면 묻지 않는다, 최대 4개)
- 질문 수는 Category·Goal과 부족한 정보에 따라 동적으로 결정
- 사용자는 질문마다 답변하거나 건너뛸 수 있다. 건너뛴 정보는 Unknown으로 남고 본문에서 생략된다.
- 질문은 선택형(버튼)을 우선 쓰고, 필요할 때만 주관식을 쓴다.
- 질문과 답변은 저장한다 (35장 SmartQuestion).

#### 예시
- **맛집:** 어떤 메뉴가 가장 좋았나요? / 다시 방문할 의향이 있나요? / 가격대는 어떻게 느꼈나요?
- **여행:** 이 장소에서 가장 기억에 남은 점은? / 방문 시기는 언제였나요? *(EXIF 촬영일시가 있으면 "○월 ○일 방문이 맞나요?"로 확인)*
- **제품:** 직접 써본 기능 중 가장 만족한 점은?

#### 목적
각 플랫폼 콘텐츠를 따로 생성하지 않고, 공통 원본 스토리를 먼저 만들어 품질과 일관성을 유지한다. **Phase 1A부터 적용한다.**

#### 데이터 구조 예시

## 9. Blog Search Quality Engine

검색 순위 조작이나 상위 노출 보장을 목표로 하지 않는다.
목표는 **검색 사용자가 읽을 가치가 있는 고품질 콘텐츠**를 만드는 것이다.

### 9.1 점검 항목
| 항목 | 판정 방식 |
|---|---|
| 핵심 키워드 반복 여부 / 밀도 | 규칙 기반 (빈도 계산) |
| 소제목 구조 | 규칙 기반 |
| 제목 길이 | 규칙 기반 |
| Search Intent 적합성 | LLM 체크리스트 |
| 제목 적합성 | LLM 체크리스트 |
| 핵심 키워드 자연스러움 | LLM 체크리스트 |
| 관련 주제 커버리지 | LLM 체크리스트 |
| 사용자 경험 반영도 | Evidence 매칭 비율 |
| 정보 구체성 / 정보 밀도 | LLM 체크리스트 |
| 사진과 본문 연관성 | Visual Fact 매칭 |

### 9.2 점수 산출 원칙
- LLM이 숫자 점수를 직접 매기지 않는다 (같은 글에도 점수가 들쭉날쭉하기 때문).
- 항목별 **통과 / 개선 필요** 판정을 모아 점수로 환산한다.
- MVP에서는 점수보다 **개선 제안 목록**을 우선 보여준다.

### 9.3 출력 예시
```text
Search Readiness: 88 / 100

검색 의도 적합성      통과
제목 적합성          통과
정보 완성도          개선 필요 — 방문 시간대 정보가 없습니다
키워드 자연스러움     통과
사진-본문 연계        통과
```

## 10. Content Quality Engine

콘텐츠는 생성 후 반드시 품질 검수를 거친다.
응답 속도와 비용을 고려해 **결정적인 점검은 코드(규칙 기반)로 처리하고, LLM 호출은 최소화**한다.

### 10.1 처리 순서
```text
AI Draft (Master Story 기반)
   ↓
① Rule-based Pre-check  (코드, LLM 미사용)
   - 금칙어 사전 매칭 (Level 1~3, Phase 2: Level 4)
   - Claim 패턴 검출 (최상급·인증·효능·가격 표현)
   - 키워드 반복 빈도 계산
   - AI 상투 표현 패턴 검출
   - 채널별 길이·해시태그 제약 점검 (4.3)
   ↓
② Contextual Review  (LLM 1회, 결과는 JSON 이슈 목록)
   - Evidence Consistency: 각 문장이 Evidence 출처와 맞는지
   - ①에서 검출된 Level 2 표현의 문맥 판단
   - Claim 근거 유무 판단
   - Search Quality 체크리스트
   - 선택 Tone 일치 여부 (Phase 2: My Voice 일치)
   ↓
③ Targeted Rewrite  (LLM 1회)
   - 이슈가 있는 문장만 수정 (전체 재작성 금지)
   ↓
④ Post-rewrite Verification
   - 수정된 문장에 ① 재실행 + Evidence 대조
   - 실패 시 해당 문장은 수정 전으로 되돌리고 사용자에게 경고 표시
   ↓
Final Output + 이슈/제안 목록
```

### 10.2 Phase 1A 최소 범위
Phase 1A에서는 다음만 구현한다. 나머지는 Phase 1C에서 고도화한다.
- 금칙어 사전 (Level 1, Level 2)
- Claim 패턴 검출 (사전 기반)
- Evidence Consistency Check
- 채널 길이 제약 점검
- ③ Targeted Rewrite + ④ 재검증

## 11. 금칙어 필터링 알고리즘

### 11.1 목적
- 광고성·스팸성 표현 제거
- 과장 표현 제거
- 허위 가능성이 높은 표현 방지
- 민감 산업 위험 표현 방지 (41.2)
- 브랜드별 금칙어 반영 (Phase 2)
- AI 상투 표현 제거
- 키워드 과다 반복 방지

### 11.2 4단계 정책

#### Level 1. 절대 금지 표현
발견되면 반드시 수정하거나 삭제한다.

예:
- 질병 치료·예방 단정: "완치", "질병 치료", "암 예방"
- 의약품 오인 표현 (식품·화장품): "염증 치료", "세포 재생", "약효"
- 수익 보장: "원금 보장", "확정 수익", "무조건 수익"
- 타사·타인 비방, 욕설·혐오 표현
- 불법 행위를 조장하는 표현

#### Level 2. 주의 표현
문맥에 따라 판단한다 (10.1 ②).

예: 무조건, 100%, 완벽한, 최고, 반드시, 절대

#### Level 3. SEO 과최적화 표현
동일 키워드 반복 여부를 확인한다 (규칙 기반 빈도 계산).

#### Level 4. 사용자 정의 금칙어 — *Phase 2*
Brand Profile / My Voice에서 사용자별로 등록한다.

### 11.3 처리 방식
```text
Dictionary Filter (코드)
      ↓
Contextual AI Review (LLM, Level 2만)
      ↓
유지 / 수정 / 삭제 판단
      ↓
해당 문장만 자연스럽게 재작성
```

### 11.4 사전 관리
- 공통 사전(서비스 제공)과 사용자 사전(Phase 2)을 분리한다.
- 업종 태그(식품, 건강기능식품, 화장품, 의료, 금융 등)별로 사전을 적용한다.
- 일치 방식: 정확 일치 / 정규식

## 12. Claim Verification

### 목적
근거 없는 최상급·효능·인증·성과 표현을 막는다.

### 주요 검토 표현

- 사용자의 주관적 평가는 "제 기준에서는", "개인적으로" 같이 의견임을 드러내는 형태로 쓴다.

## 15. 네이버 블로그 지원

### 15.1 정책
네이버 블로그는 외부 글쓰기 API를 지원하지 않는다고 전제한다.
따라서 본 서비스는 **자동 게시 기능을 구현하지 않는다.**

### 15.2 제공 기능

#### Rich Text Copy
- 제목, 문단, Bold, 리스트, 줄바꿈, 이미지 위치 마커
- 구현: Clipboard API로 `text/html`과 `text/plain`을 동시에 기록 (HTTPS 환경 필수)

#### Plain Text Copy
- 순수 텍스트
- 서식 호환 문제가 생길 때 사용

#### 이미지 일괄 다운로드
- 이미지는 클립보드로 함께 넘어가지 않는다고 전제한다.
- 본문의 `[사진 N 삽입]` 마커와 번호를 맞춘 **ZIP 다운로드** 제공
  - 파일명 예: `01_매장외관.jpg`, `02_파스타.jpg`
- 다운로드 이미지는 EXIF(GPS 포함)가 제거된 버전이다.

### 15.3 출력 예시
```text
[사진 1 삽입]

**매장의 첫인상**

본문...

[사진 2 삽입]

**제가 주문한 메뉴**

본문...
```

### 15.4 사전 검증 (PoC) — Phase 1A 착수 시 우선 수행
네이버 스마트에디터에 붙여넣었을 때의 동작을 실제로 검증하고, 결과에 따라 Rich Copy 범위를 확정한다.

| 소제목 | 제목 서식 유지 / 일반 텍스트로 변환 여부 |
| 글머리표·번호 리스트 | 유지 여부 |
| 줄바꿈·문단 간격 | 의도대로 반영되는지 |

## 19. 프로젝트 관리 기능

각 콘텐츠 작업은 독립적인 프로젝트로 관리한다.

### 19.1 프로젝트 항목
프로젝트명, Category, Goal, Tone, Platform, 생성일, 수정일, 사진, Quick Text, Smart Question 답변, Master Story, 채널별 콘텐츠(Blog / Facebook / Instagram / Shorts), 상태

### 19.2 상태
| 상태 | 정의 |
|---|---|
| Draft | 입력 중, 생성 전 |
| Generated | AI 생성 완료 |

## 27. 외부 API / 서비스 연동 전략

### 원칙
- OpenAI API를 제외한 유료 API는 사용하지 않는다.
- 무료 API / 무료 쿼터 / 오픈소스를 우선한다.
- **외부 API 약관·쿼터는 개발 착수 직전에 다시 확인**하고, 그 결과를 45장 미결 사항에서 종결 처리한다.

### 27.1 OpenAI API — MVP 필수
| 용도 | 비고 |
|---|---|
| 이미지 분석, Evidence 추출 | 분석용 리사이즈 이미지 사용 (40.5) |
| Smart Question, Master Story | Structured Output(JSON Schema) |
| Blog 생성, 플랫폼별 변환 | - |
| Contextual Review, Targeted Rewrite | 10장 ②③ |
| 제목/CTA/Hashtag 생성 | - |

- 작업별로 모델을 나눠 쓴다: 분류·점검은 경량 모델, 본문 작성은 상위 모델 (모델 선정은 45장 미결 사항)

### 27.2 Pixabay API — Phase 1C
- 용도: 무료 이미지·영상 검색, 블로그 보조 이미지, Shorts 보조 미디어
- 약관상 주의 (재확인 필요): 검색 결과를 보여줄 때 출처 표시. 이미지 URL을 계속 직접 링크하지 말고 **서버로 내려받아 자체 저장**

### 27.3 Unsplash API — Phase 1C
- 용도: 여행, 라이프스타일, 카페, 배경·커버 이미지
- 약관상 주의 (재확인 필요): **Unsplash가 제공한 이미지 URL을 그대로 사용**, 사용자가 이미지를 선택하면 다운로드 추적 엔드포인트 호출, 작가와 Unsplash 출처 표기. 데모 단계의 요청 한도가 낮아 운영 전 승인 신청 필요

> Pixabay와 Unsplash는 저장 방식이 반대이므로 `ProjectImage.source`에 따라 저장·출력 로직을 분리한다.
> 네이버 블로그용 ZIP에는 내려받기가 허용된 이미지만 포함한다.

### 27.4 NAVER Search API — Phase 2
- 용도: 블로그 검색 결과 분석 (23장 범위로 한정)
- 일일 호출 한도 확인 필요

### 27.5 Meta Graph API — Phase 2
- 용도: Facebook Page 게시, Instagram Professional 계정 게시
- 주의: OAuth, 권한 설정, 앱 심사, 계정 유형 처리, 게시 이미지의 공개 URL 필요

### 27.6 YouTube Data API — Phase 2
- 용도: YouTube Shorts 업로드, 제목/설명/메타데이터 등록
- 주의 (재확인 필요):
  - 감사(audit)를 받지 않은 API 프로젝트는 업로드 영상이 **비공개로 제한**됨 → 공개 서비스 전 감사 신청 필요
  - 할당량이 프로젝트 단위로 매겨지고 업로드 비용이 커서 **서비스 전체의 하루 업로드 건수가 제한적** → 할당량 증설 신청 필요

### 27.7 FFmpeg — Phase 2 (오픈소스)
- 용도: 사진 → 슬라이드 영상, 이미지 + 영상 결합, 자막, 음악, 9:16 Shorts 출력
- 주의: 처리 시간이 길어 요청-응답이 아닌 **비동기 작업(Job)**으로 처리하고, 서버리스 실행 시간 제한을 확인해야 함

```text
사용자 수정 (섹션 재생성 포함)
   ↓
Copy / ZIP 다운로드 / Save
   ↓
(직접 게시 후) 게시 완료 표시
```

## 38. 개발 우선순위

### Phase 0 — 사전 검증 (1A 착수 전 또는 초기)
- 네이버 스마트에디터 붙여넣기 PoC (15.4)
- 외부 API 약관·쿼터 재확인 (27장)
- 생성 1건당 LLM 호출 수·비용 측정 프로토타입 (40.5)

### Phase 1A — 핵심 콘텐츠 품질 검증 (사진 → Blog)
**개발:**
- 이미지 업로드 (리사이즈, EXIF 처리)
- Quick Text, Category / Goal / Tone / Platform
- Evidence Engine
- Smart Question
- **Master Story**
- Blog Writer (섹션 재생성 포함)
- Quality Engine 최소 범위 (10.2)
- Rich / Plain Copy, 이미지 ZIP 다운로드
- 콘텐츠 버전, EventLog, UsageLog

**성공 기준:**
> 사용자가 "이 정도면 거의 고치지 않고 블로그에 올릴 수 있다"고 느끼는가? (Copy-ready Rate로 측정, 39장)

### Phase 1B — Multi-channel
**개발:** Master Story 기반 Facebook, Instagram, YouTube Shorts Script 변환

### Phase 1C — 품질 고도화
**개발:** Search Quality, Keyword Stuffing, Generic AI Phrase, Claim Verification 고도화, 민감 산업 사전 확장, Publish Readiness, 스톡 이미지 검색 (8.3 정책)

> **MVP 출시 = Phase 1A + 1B + 1C 완료**

### Phase 2A — Personalization
My Voice, Brand Profile, 사용자 정의 금칙어(Level 4), Content Memory

### Phase 2B — Publishing
Meta Graph API, YouTube Data API(감사·할당량 신청 포함), OAuth, Scheduling, Job Queue

### Phase 2C — Video
FFmpeg, 사진 기반 Short Video, 자막, 9:16 MP4

### Phase 2D — Analytics
성과 데이터, Content Calendar, Performance Learning, 다음 콘텐츠 추천, NAVER Search API 기반 Blog Intelligence

## 39. MVP 성공 지표

### 39.1 Product
- 콘텐츠 생성 완료율
- 생성 후 Copy 비율
- 사용자 수정량
- 재생성 비율 (전체 / 섹션)
- 프로젝트 재방문율
- Smart Question 건너뛰기 비율

### 39.2 Quality
- 사용자가 수정한 문장 비율
- Unsupported Fact 발생률 (Evidence 출처가 없는 문장 비율, 샘플 수동 검수 병행)
- 금칙어 검출률
- Search Quality 개선 제안 반영률
- Post-rewrite Verification 실패율

### 39.3 핵심 KPI — Copy-ready Rate
> 생성된 콘텐츠 중 사용자가 큰 수정 없이 복사한 비율

**측정 정의:**
- 분자: Copy 이벤트(`copy_rich` / `copy_plain`) 시점의 버전과 AI 최종 생성 버전의 **편집 거리 비율이 X% 이하**인 콘텐츠 수
- 분모: AI 생성이 완료된 콘텐츠 수
- 기준값 X는 45장 미결 사항에서 확정 (초기 가설: 10%)
- 데이터 출처: ContentVersion, EventLog

## 40. 비기능 요구사항

### 40.1 성능
- 주요 페이지 초기 로딩 최적화
- 생성 중 **단계별 진행 상태 표시** (분석 → 질문 → 스토리 → 작성 → 검수)
- 이미지 업로드 최적화 (클라이언트 측 사전 리사이즈 검토)

### 40.2 안정성
- AI 응답 실패 시 Retry (지수 백오프, 최대 횟수 제한)
- API Timeout 처리
- 임시 저장, 자동 저장
- 단계별 결과 저장 (중간에 실패해도 처음부터 다시 생성하지 않음)

### 40.3 보안
- API Key는 서버에만 보관, Client 노출 금지
- 사용자 콘텐츠 접근 제어 (Supabase Row Level Security)
- 업로드 파일 검증: 확장자 + MIME + 파일 시그니처, 최대 용량 제한
- HTTPS 필수 (Clipboard API 요구사항 포함)

### 40.4 개인정보
- 사용자가 업로드한 이미지와 텍스트를 다른 사용자의 콘텐츠 생성에 사용하지 않음
- 프로젝트별 접근 권한 분리
- 이미지 저장 전 **EXIF(GPS 포함) 제거**
- 사진에 사람 얼굴 등 타인이 식별될 수 있는 요소가 감지되면 게시 전 확인 안내 (41.2)
- 프로젝트 삭제 시 관련 이미지·로그 삭제 정책 정의

### 40.5 비용 통제
| 항목 | 정책 |
|---|---|
| 이미지 입력 | 분석용 저해상도 사본만 OpenAI에 전송 |
| 호출 수 | 생성 1건당 LLM 호출 수 상한 설정 (Quality Engine 최대 2회 + 재검증) |
| 모델 분리 | 분류·점검은 경량 모델, 본문은 상위 모델 |
| 사용자 한도 | 사용자별 일/월 생성 횟수, 재생성 횟수 한도 |
| 모니터링 | UsageLog로 생성 1건당 비용 집계, 임계치 초과 시 알림 |
| 수치 | 목표 비용·한도 수치는 Phase 0 측정 후 확정 (45장) |

## 41. AI 생성 정책 및 법적 고려

### 41.1 AI 생성 필수 정책
1. 사용자에게 없는 경험을 지어내지 않는다.
2. 사진에서 확실히 확인되지 않는 내용을 사실처럼 쓰지 않는다. (관찰 표현의 완곡 허용 범위는 7.2 참조)
3. Unknown 정보는 필요하면 질문하고, 답이 없으면 생략한다.
4. 과장 표현은 근거가 있을 때만 사용한다.
5. 사용자의 평가와 객관적 사실을 구분한다.
6. 스톡 이미지를 사용자 경험의 증거로 사용하지 않는다.
7. 경제적 이해관계가 있는 콘텐츠는 표기한다.
8. 상위 검색 노출을 보장하지 않는다.
9. 플랫폼 탐지 우회를 목표로 하지 않는다.
10. 실제 독자가 읽기 좋은 고품질 원문 작성에 집중한다.

### 41.2 법적 표기 및 민감 산업
> 아래 정책은 서비스 출시 전 법률 검토가 필요하다.

#### 광고·협찬 표기
- 입력 단계에서 "광고·협찬 여부(경제적 이해관계)"를 선택하게 한다.
- 체크하면 채널별로 제목 또는 본문 첫머리에 표기 문구를 자동으로 넣는다 (예: "본 게시물은 ○○으로부터 제품을 제공받아 작성했습니다").
- 관련 기준: 공정거래위원회 「추천·보증 등에 관한 표시·광고 심사지침」

#### 민감 산업 정의 (업종 태그)
| 업종 | 주요 위험 표현 |
|---|---|
| 건강기능식품 / 일반식품 | 질병 예방·치료 효능 표현 |
| 화장품 | 의약품 오인 표현, 기능성 범위를 넘는 표현 |
| 의료·의약품·의료기기 | 치료 효과 보장, 체험기 형태의 의료 광고 |
| 금융·투자 | 수익 보장, 원금 보장 |
| 부동산 | 확정 수익, 개발 호재 단정 |

- 업종 태그가 있는 프로젝트에는 해당 업종 사전(Level 1)을 추가로 적용한다.
- MVP에서는 Category·Goal과 Quick Text를 보고 업종을 추정하여 사용자에게 확인받는다 (Phase 2: Brand Profile 업종 태그).

#### 초상권·개인정보
- MVP: 업로드 화면에 타인 얼굴·차량번호·개인정보 노출 주의 안내. 이미지 분석에서 사람 얼굴이 감지되면 경고 표시
- Phase 2: 자동 블러 처리 검토
